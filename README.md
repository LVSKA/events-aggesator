# events-aggregator

Backend-сервис на Django + DRF, синхронизирующий события с внешним
Events Provider API и предоставляющий свои REST-эндпоинты для событий,
свободных мест и регистрации/отмены регистрации.

## Стек

- Python 3.12, Django 5, Django REST Framework
- PostgreSQL — хранилище событий/билетов
- Celery — фоновая синхронизация, broker — Postgres (kombu sqlalchemy-transport,
  без Redis)
- uv — управление зависимостями, ruff — линтер

## Структура

```
src/
├── core/             # settings, celery app, корневые urls
├── events_provider/  # EventsProviderClient + EventsPaginator - весь HTTP
│                       к внешнему API живёт только тут
├── events/           # события и площадки: модели, вьюхи, бизнес-логика
├── tickets/          # регистрация/отмена регистрации
└── sync/             # фоновая и ручная синхронизация с внешним API
```

Подробное описание архитектурных решений — в `architecture-plan.md`
(в этом же проекте, на верхнем уровне репозитория).

## Локальный запуск

```bash
cp .env.example .env       # заполнить EVENTS_PROVIDER_API_KEY и остальное
docker compose up -d db
uv sync
uv run ./manage.py migrate
uv run ./manage.py runserver
```

Фоновый воркер (в отдельном терминале):

```bash
uv run python -m celery -A core worker -P solo -B -l INFO
```

## Тесты и линтер

```bash
uv sync --extra dev
uv run pytest
uv run ruff check .
```

Тесты `EventsProviderClient` и `EventsPaginator` мокируют HTTP полностью
(`unittest.mock`), реальная сеть им не нужна. Тесты бизнес-логики
(`events`, `tickets`, `sync`) используют `pytest-django` и реальную БД
(через фикстуру `--reuse-db` можно ускорить повторные прогоны).

## Endpoints

| Endpoint | Метод | Описание |
|---|---|---|
| `/api/health/` | GET | health check |
| `/api/sync/trigger/` | POST | запустить синхронизацию вручную (ставит celery-таск) |
| `/api/events/` | GET | список событий из локальной БД (`date_from`, `page`, `page_size`) |
| `/api/events/{id}/` | GET | детали события из локальной БД |
| `/api/events/{id}/seats/` | GET | свободные места, идёт во внешний API напрямую, кэш 30 сек |
| `/api/tickets/` | POST | регистрация на событие |
| `/api/tickets/{ticket_id}/` | DELETE | отмена регистрации |

## Важные нюансы, которые учтены в коде

- Все обращения к внешнему API — trailing slash, курсор для пагинации
  берётся из `next` (полный URL), а не собирается вручную
- Перед запросом мест и перед регистрацией код сам проверяет
  `event.status == "published"`, чтобы не словить кривой 500 от провайдера
- Ticket ID у провайдера привязан к месту, а не к пользователю — повторная
  регистрация на то же место после отмены может вернуть тот же `ticket_id`;
  `tickets.logic.create_ticket` использует `update_or_create`, чтобы это
  не приводило к падению на дубликате первичного ключа
- Синхронизация инкрементальная: `SyncMetadata` хранит `last_changed_at`,
  первый прогон стартует с `2000-01-01`

## Известное ограничение

Кэш свободных мест (`events.logic.get_available_seats`) использует
дефолтный `django.core.cache` backend (по процессу). Если веб-сервер
поднят с несколькими worker-процессами (как в `run.sh`), кэш не будет
общим между ними — TTL в 30 секунд от этого не ломается, но каждый
процесс какое-то время хранит свою копию. Для одного контейнера/процесса
это не проблема; при масштабировании стоит вынести кэш в отдельный
shared backend.

## Заметка о том, как собирался этот проект

Код в этом репозитории был написан за один присест без доступа к
интернету (нельзя было поставить зависимости и реально прогнать
`pytest`/`ruff`). Логика по каждому модулю проверена вручную и должна
быть рабочей, но перед тем как считать задание готовым — обязательно
прогоните тесты и линтер локально и почините то, что вылезет.
